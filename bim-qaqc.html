BIM Model QA/QC Automation Platform

How I turned a manual model-review process into an automated pipeline: an 800+ rule compliance engine, two-pass clash detection with resolution suggestions, and one-click fix execution that writes corrections back into the Revit model, all running headlessly in the cloud.

The problem

Model review was a human bottleneck

Before a Revit/BIM model goes to fabrication or construction, someone has to check it: are elements configured to the project standards, are systems routed without collisions, is the data on each element complete and consistent? Done by hand, that means an engineer clicking through a model with tens of thousands of elements against hundreds of written requirements. It is slow, it does not scale across projects, and the clashes that slip through are found on site, where they are most expensive to fix.

The goal was to make that review automatic: upload a model, get back a scored report of every violation and clash, and where possible, let the platform fix the model itself.

The system

From model to fixed model in five stages

The platform is split between a C# rule and clash engine that runs inside headless Revit on Autodesk Platform Services (Design Automation), and a Python service that manages jobs, normalizes results, and serves the dashboard and interactive reports.

1

Pick a model, pick a rule pack

From the dashboard, a reviewer selects a cloud-hosted Revit model and the rule set for that project. The Python service filters rules by sensitivity tier and submits a Design Automation job.

2

Headless extraction and rule evaluation

In the cloud sandbox, the C# addin opens the model without a UI, extracts every relevant element with its parameters and geometry, and evaluates 800+ expression-based compliance rules against them.

3

Two-pass clash detection

A fast bounding-box pass finds candidate collisions across all system pairs, then a precise geometry pass verifies real intersections. An analyzer matches each clash against resolution rules and proposes ranked fixes.

4

Interactive report

Results come back as structured JSON plus a pre-rendered clash section. The service builds a self-contained report: compliance score, issues by category and severity, and per-clash resolution plans with code references.

5

One-click fix execution

The reviewer approves suggested fixes in the report. A second cloud job reopens the model, applies the approved corrections through registered fix handlers, and saves a corrected version, while the report polls live status.

Engineering deep dives

Three problems worth telling

Deep dive 01

Killing false positives without killing coverage

An automated checker that cries wolf gets ignored, and early on this one did. The worst case: a material-transition rule referenced parameters that fabrication elements do not carry, and a rule that fails to evaluate was being counted as a violation. One run flagged all 25,843 pipe fittings and accessories in a model at once.

Two changes fixed the trust problem:

  • Safe evaluation. Parameter access went through null-safe helpers, so a rule that references data a model does not have resolves cleanly instead of failing into a false violation.
  • Sensitivity tiers. Every rule was classified into three tiers: geometry and clash checks always run, configuration checks run by default, and metadata or empty-field checks are opt-in because they are the noisiest. A classification script keeps the tiers in sync as the rule library grows, and the reviewer chooses the tier per run.

The result is a report where a flagged issue is worth reading, which is the difference between a tool people use and a tool people bypass.

Deep dive 02

Clash detection that fits a cloud time budget

Checking every element pair for geometric intersection is far too slow for models of this size, and cloud jobs have hard time limits. The engine runs in two passes: a cheap bounding-box sweep first cuts the candidate set down by orders of magnitude, then exact solid-geometry intersection runs only on those candidates. Analytics on top group the results into system pairs and rank the worst offenders, so a reviewer sees the twenty clashes that matter instead of a wall of raw hits.

Each verified clash then goes through a resolution analyzer driven by a versioned JSON rulebook: eight strategies, from vertical and horizontal offsets to elevation swaps and coordination RFIs, each scored per system pair and annotated with the code references that justify it.

Deep dive 03

Closing the loop: fixes that write themselves back

Reporting a clash is useful; fixing it is the product. Approved resolution plans are compiled into fix definitions and sent to a second headless Revit job, where a registry of fix handlers applies the matching strategy, moving a duct up, offsetting a pipe run, swapping elevations, inside a real Revit transaction, then saves the corrected model.

Making that reliable meant designing for the sandbox's constraints: signed upload and download URLs expire in 60 minutes, jobs can sit in a queue behind other tenants, and a partial fix run must never corrupt the model or the report. The report's embedded JavaScript polls job status with backoff and renders per-fix success or failure when the run completes, so the reviewer watches the loop close from the same page.
